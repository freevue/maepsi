# 초기 조사와 질문 기준

이 문서는 setup이 사용자 프로젝트에 맞는 질문을 고를 때 읽습니다. 아래 항목은 질문 후보이며 프로젝트에 자동 적용하는 디자인 규칙이 아닙니다.

## 먼저 확인할 자료

- 사용자 제공 디자인 원본, 선호·비선호 화면과 현재 제품의 대표 화면을 찾습니다. 원본을 볼 수 없으면 그 사실을 기록합니다.
- 색상 원시값과 의미별 토큰, 글꼴·크기·굵기, 간격·크기·모서리·그림자, 아이콘·이미지, 움직임 설정을 찾습니다. 선언만 있는 값과 실제 화면에서 쓰는 값을 구분합니다.
- 공용 UI 컴포넌트와 화면 전용 요소를 구분합니다. 공용 컴포넌트의 공개 props·속성, 기본값, 변형, 상태, 이벤트, 사용하는 토큰과 사용처를 조사합니다.
- 대표 화면에서 데스크톱·좁은 화면, 기본·로딩·빈 결과·오류·비활성·포커스 상태 중 실제로 확인 가능한 범위를 기록합니다.

## 사용자에게 묻는 방법

조사한 화면이나 코드 값을 먼저 보여주고 결정이 필요한 것만 묻습니다. 한 번에 관련 질문 2~4개를 묶습니다. 막연한 취향 대신 현재 사례와 선택지를 사용합니다.

예를 들어 검색 화면의 버튼은 의미별 강조 토큰을 쓰고 설정 화면의 같은 역할 버튼은 원시 색상값을 쓴다면, 두 화면을 보여주고 통일할지 의도적인 차이로 둘지 묻습니다. 공용 버튼의 한 변형이 여러 화면에 쓰이는데 문서가 없다면, 그 변형을 정식 계약으로 둘지 먼저 확인합니다.

1. **방향:** 현재 화면에서 유지할 부분과 어색한 부분은 무엇인가요? 참고할 화면과 피할 화면은 무엇인가요? 제품이 차분함·밀도·강조 중 무엇을 우선해야 하나요?
2. **색·타입·형태:** 실제 사용 중인 색의 역할과 대비, 제목·본문의 위계, 간격의 밀도, 모서리·그림자·아이콘 방식 중 어떤 것을 표준으로 둘까요? 테마별 예외가 있나요?
3. **컴포넌트:** 같은 기능에 기존 컴포넌트를 언제 재사용하고 언제 새 변형을 만들까요? 새 컴포넌트의 props는 어떤 시각적 선택을 허용하고 무엇을 고정할까요?
4. **화면 사용:** 주요 행동과 정보의 우선순위, 로딩·빈 화면·오류의 문구와 행동, 작은 화면의 재배치, 포커스·키보드 조작과 움직임의 강도를 어떻게 정할까요?

답변이 없는 항목은 `미결정`으로 남깁니다. 기존 구현은 `관찰`로 기록하며 사용자 승인 없이 표준으로 승격하지 않습니다.

## 가이드에 제안할 세부 주제

필요한 주제만 실제 전후 사례와 함께 제안합니다. 사용자가 채택한 선택만 사용 가이드의 규칙이 됩니다.

- **색상:** 원시값과 의미별 토큰의 관계, 배경·텍스트·강조·상태색의 용도, 테마별 대응.
- **타이포그래피:** 제목과 본문의 위계, 줄바꿈과 긴 텍스트, 숫자 정렬, 문구의 대소문자와 버튼 이름.
- **배치:** 정보 그룹 사이의 거리, 시각적 정렬, 중첩 요소의 모서리 관계, 화면별 밀도와 주요 행동의 위치.
- **상호작용:** hover·focus·pressed·disabled, 로딩·빈 화면·오류의 피드백, 움직임의 목적·속도·중단 가능성.
- **접근과 반응형:** 의미 있는 HTML 요소, 키보드·포커스, 이미지 설명, 대비, 좁은 화면의 순서와 터치 영역.

각 규칙에는 적용 대상, 채택 이유, 좋은 예와 피할 예, 검증 가능한 관찰 기준을 적습니다. 수치나 취향은 프로젝트에서 결정한 것만 넣습니다. 화면이 어색하다는 인상만으로 위반을 만들지 않고, 근거가 부족하면 사용자에게 선택을 묻습니다.

[Interfaces의 치트 시트](https://interfaces.dev/cheat-sheet)와 [디테일 사례](https://interfaces.dev/magazine/issues/details-that-make-interfaces-feel-better)는 전후 비교와 질문 방식의 참고 자료입니다. 그곳의 개인적 선호나 수치를 프로젝트의 기본 규칙으로 복사하지 않습니다.

## setup 완료 조건

- 진입 문서에서 확정된 토큰·컴포넌트·사용 가이드의 정본을 정확히 찾을 수 있습니다.
- 조사 범위의 공용 디자인 컴포넌트마다 props·속성의 용도와 상태를 설명하는 문서가 있거나, 빠진 대상과 이유가 보고되어 있습니다.
- 가이드의 강제 규칙은 사용자 결정이나 충돌 없는 프로젝트 정본에 근거합니다. 관찰·미결정은 강제 규칙과 분리됩니다.
- 문서 링크와 값의 충돌을 검사했습니다. 코드와 실제 화면을 확인한 범위, 확인하지 못한 범위를 따로 보고합니다.

빠진 공용 컴포넌트 문서나 필수 사용자 결정이 있으면 `부분 구성`으로 보고합니다. 자동으로 `완료`라고 말하지 않습니다.
